# Revision options: how they're checked, and how well they work

The detail behind the README's [Revision options](../README.md#revision-options-after-a-dropout) summary.


When someone leaves, the organizer chooses **Suggest options**. With `OPENAI_API_KEY` set, a model reads the group chat and proposes up to three options. Each option picks a cabin and can include a spending limit a person stated about themselves, quoted from their own message. The model interprets meaning, so “I can’t go above $170” counts as a $170 limit. The app renders the explanation from verified listing details and computed shares. It never receives anyone’s saved private budget.

Code then decides what is shown:

- Every quote must appear in that person’s own message.
- Every amount must be literally written there, as digits or as spoken words such as “two hundred dollars”.
- The cabin must fit the group.
- Shares and top-ups are computed by the same allocator that publishes versions.
- Option titles, explanations and trade-offs are generated from verified listing details, shares and approval requirements. Provider prose cannot claim that everyone approved or guarantee a booking. Checked source quotes explain each person's preferences.
- Questions may only repeat amounts written by their addressee. A firm stated ceiling suppresses redundant questions about stretching beyond it; uncertainty about cabin choice or attendance can still be clarified.
- A reason is judged and shown as the **full sentence** it comes from, not the model's chosen fragment, so “want to pay more for Pine & Still” cut from “I really don't want to pay more for Pine & Still” is still read as a refusal.
- A reason is shown as **Why** only if it still supports that option. Other verified quotes stay visible, labelled: “points to another option” (it names a different cabin, or a limit below this option's share), “argues against this option” (“please not Pine & Still again”, “Pine & Still is not for me”, or “I don't want to pay any more” on an option that raises that person's share), or “earlier message, since replaced” (an amount, cabin preference or explicit correction the same person later changed). Reasons must be real phrases, not a name or a two-word fragment. A verified message about a cabin is shown on every card it bears on, not only the card the model attached it to; those added by code are marked “matched by code”.
- The model may only ask about money, attendance or cabin choice; questions about rooms, beds or arrival times are dropped.
- Chat exports with timestamps (“[10/7/26, 9:41 PM] Maya: …”, “Maya, 9:41 PM: …”), WhatsApp on iPhone's invisible leading mark and its “~ Maya” for unsaved contacts keep their speakers.
- Failing suggestions are listed as discarded, and ambiguity becomes a clarification question.
- The plain rebalance is always included for comparison.

If a person’s stated limit sets their share in an option, that option can’t be published until they explicitly confirm the limit in their own view (**Send Maya a confirmation request**). If, once those confirmations are in, saved budgets still can't cover the split, the card asks whoever wrote a higher limit than the split needs (their saved budget may be lower) instead of ending at “cannot cover”. Confirming makes it their saved budget. Options are stored on the server and published by ID, so neither the shares nor the “suggested by” record come from the browser. Publishing recomputes the split from saved budgets and refuses if anything changed, before any real authorization is released. Each person then approves their own new share and top-up.

Privacy: the model never receives saved budgets, and nothing compares a proposed limit with anyone’s private budget. While an option still waits on someone’s confirmation, its preview is computed only from limits stated in the chat and the cabin total. Saved budgets don’t enter it, so chat the organizer writes can’t steer a preview into revealing one. Once nothing is waiting, the preview is exactly the split that publishing produces from saved budgets. That split is fixed for each cabin, so chat input can’t probe it, and it reveals only what a published split would. Option requests are also limited to five per plan version, and each is recorded in Activity with the amounts read from the chat. Confirmed limits and open requests are visible only to their owner and the organizer, and the shared activity log records that someone confirmed, not the amount. When someone types a firm limit in answer to a question, the organizer sees only that they answered; if that limit caps their share, the share will equal it, as with any budget.

Requests go to the person, not the organizer’s screen: **Send Maya a confirmation request** puts a card at the top of Maya’s own view, quoting her message, and an uncertain message gets **Ask Maya for a firm limit**, which asks her to type one. A one-click confirmation can lower a saved budget but never raise it, because the organizer wrote the pasted chat; raising it is a separate budget edit. Requests belong to one plan version and expire when a new one is published. **Not now** is recorded for the organizer, and an answer shows on the organizer’s card as “answered”. Each AI option lists its reasons as quotes from people’s own messages (“Why: … — Alex, line 7”), and the panel shows the checked reasons behind each option. An option with the same split as the plain rebalance is tagged as such: “Standard rule” when the model gave no verified reasons for it, or “AI suggestion · same split as the standard rule” when it did. A local-planner option that matches the rule says “same as the local planner”, never “AI”. When a confirmation makes two cards identical, they become one card that says why. Code also flags a firm limit no option uses, and marks any option that asks someone for more than they wrote.

Without a key, or if the model fails, a **local planner (not AI)** takes the latest dollar amount each person wrote, without interpreting wording. Anyone whose share depends on it must confirm.

`npm run eval:revisions` runs 12 frozen briefs from the PRD acceptance spec (clear, ambiguous, infeasible, adversarial) through the real verifier using hand-written reference answers, two of them deliberately unsafe. [`eval/revision-results.json`](../eval/revision-results.json) records 12/12 with no unsafe option shown. This benchmark measures verifier behavior with reference and injected outputs; live provider runs are recorded separately. `npm run eval:revisions:live -- --write` measures the configured model (gpt-4.1-mini: about 2–6 s per brief, 4–6 s on the demo chat). In no live run could a publishable option exceed a saved budget, because every limit stated in chat needs its owner's confirmation and publishing recomputes from saved budgets. The stricter display-safety check drove the ambiguity backstop below: the pre-backstop fresh set recorded [5/6 safe](../eval/revision-holdout2-results-live-baseline.json), with a hedged “$160ish” displayed as a pending limit. The backstop routes that phrasing to clarification.

**Ambiguity backstop.** Some messages are too uncertain to use as a limit whatever the model says. If every sentence stating the amount is hedged (“probably $160ish?”, “I guess $170”, “~$170”), states something other than a ceiling (“I can’t do $170”, “at least $170”), gives two amounts (“$175 or $185”), contradicts the person’s later message, reports someone else’s limit (“Jordan said $170 is fine”), or reads like an instruction to the system, code removes it from every option. Amounts that aren’t a ceiling (“I already sent you $50 for gas”, “$100 a night”, “I’m no longer capped at $170”, “$170 is fine for me”) and abbreviations like “$1.2k” are never offered as one-click limits. Code then asks that person a question, labelled “flagged by code”. It also checks each person’s latest amount itself, so an uncertain one is questioned even if the model ignored it. Firm limits, an updated figure (“make that $190”) and an unrelated “might” in another sentence pass through.

**Benchmark design.**

- The frozen set and first held-out set serve as development and regression fixtures; the fresh six provide a separately recorded comparison.
- The [fresh six](../eval/revision-cases-holdout2.json) were committed and run before the backstop existed. Their provenance and expected checks are recorded with the fixtures.
- The corpus contains developer-authored synthetic briefs, with one committed provider result per round. Rounds on similar code gave 25/26, 24/26, 26/26, 24/26, 24/26 and 25/26 (rounds six, seven, eight, nine, eleven and twelve), a recorded range of 24–26/26.
- For an ambiguous brief, “useful” counts any clarification question; it doesn't check that the question goes to the right person or that the reasons are good. From round twelve, results also report `passedFromSource`, counting only questions the model asked and options it proposed: 24/26 that round, against 25/26 for model plus code. Budget safety holds by construction, because a publishable option is always recomputed from saved budgets.
- The [no-AI local planner, run through the same checks](../eval/local-planner-baseline.txt), is useful on 23/26 and safe on 26/26 ([`scripts/local-planner-baseline.mjs`](../scripts/local-planner-baseline.mjs)), against the model’s 24–26/26. It also produces the sample chat’s $170 / $215 / $215 table. The allocator supplies the same share calculations to both paths. The no-amount benchmark below measures interpretation and clarification separately.
- The model now labels each limit it proposes as firm, hedged, a minimum, not a limit, or relayed; code keeps a limit only if the model says firm **and** the keyword backstop finds nothing.
- Financial willingness is shown through source-checked **Why** quotes and participant confirmation. Free-text model summaries are excluded.
- The keyword backstop handles common ambiguous phrasings. Per-person confirmation and recomputation from saved budgets enforce the financial guarantee.


## What the model adds: briefs with no dollar amount

The no-amount benchmark exercises interpretation, source attribution and question targeting across ten briefs whose deciding message has no figure: “I can stretch a bit”, “please not Pine & Still again”, “Maya told me she really doesn't want Creekside”, “I'll cover a bit of Maya's share”. Each brief says who should get a question, whose words should back which cabin, and which objection must never appear as a **Why** for the option it objects to. **Strict scoring.** The [strict scorer](../scripts/evaluate-noamount-strict.mjs) checks that an objection cannot support the option it opposes and records how many questions reach the person named in each brief. It was committed before the strict run; the original scorer remains available for comparison. The verifier applies the objection check even when a source quote is also tagged as a limit.

**Benchmark scope.** These ten developer-authored synthetic briefs measure interpretation of no-amount messages, source attribution and question targeting. The local planner extracts amounts and now adds code-labelled questions for explicit refusals and relayed preferences; it supplies no model-authored reasons. The [committed transparent rules comparator](../scripts/noamount-rules-baseline.mjs), developed on these briefs, achieves 10/10 with all six required questions; the [next comparison](EVALUATION_PROTOCOL.md) freezes both approaches before collecting independently authored briefs. After round eleven, a model question goes to the person whose message it cites (or whom a relayed line names), questions tied to nobody's message are dropped, and code itself asks “how far could Jordan go?” when someone offers to pay more without a number. The model then scored 8/10 with all 3 of its questions reaching the right person; code-raised questions are counted separately. Routing was refined using this development set. The frozen comparison protocol evaluates generalization on separately authored input.

## Current checks and the next comparison

The initial **Find the preferences** draft uses fixed summary text and each speaker's actual words. Mentioned expenses, deposits and repayment floors require clarification rather than becoming ceilings. The revision path adds a code-labelled question when a nonnumeric refusal or relayed preference lacks the person's own answer. These changes are covered by local regressions; the model rows above retain their original provider-run provenance.

The strict scorer now reports both question precision and recall: how many necessary questions the model emits and how many the whole model-plus-code pipeline supplies. Precision alone excludes missing questions. Rescoring preserves the source identity of the original output.

Run `node scripts/noamount-rules-baseline.mjs` for the transparent rule comparator, or pass `--cases path/to/briefs.json` for a compatible corpus. It uses speaker attribution, quoted cabin preferences and targeted clarification; it makes no model calls. The development result establishes a capable alternative for this corpus. [The comparison protocol](EVALUATION_PROTOCOL.md) freezes both approaches before independently authored briefs are supplied, and scores missed questions, recipients, reasons and effort separately.


### October 14 implementation checks

Regression tests cover pending capture reads across restart, mixed refund receipt totals, retracted preferences, generated option prose and questions that respect firm ceilings. The strict scorer now embeds the entire original run, including untrusted structured proposals, verified outputs, requested and returned model identifiers, request settings, timing, usage and fallback outcomes. Dated output files preserve each run independently. Recipient precision remains a routing measure; inspect the saved question text for meaning and usefulness using the [evaluation protocol](EVALUATION_PROTOCOL.md).
